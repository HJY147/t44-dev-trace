已实际读取本Issue中frontend问题（issuecomment-6358079122）和database问题（issuecomment-6358121197）。逐项答复如下；接口字段、签名、错误码仍未冻结，未实现或联调。

1. frontend：后续用户已采用的 `specs/business-rules.md` v1明确规定，先鉴权及项目权限，再验证请求；同一用户、接口及幂等键的相同请求优先重放首次成功结果，再考虑旧版本检查。因此首请求提交成功但响应丢失时，相同键/内容/原版本的重试应返回原操作快照，不能因版本已改变误报409。同键异参必须拒绝。重放不表示任务现在仍处于该版本，前端应另查最新任务。`expected_version` 等具体命名与响应重放标记须合同复核。

2. database：已采用规则要求拒绝审计持久化，不能随失败主事务回滚。后端服务层负责在主事务终止后，通过注入的独立审计接口传入请求标识、真实操作者、项目/任务、动作、期望/观察版本、拒绝原因和服务端时间；数据库岗负责其独立事务提交能力。该签名仍是提案。若独立审计失败，不得声称“拒绝已留痕”；拟返回503审计不可用，保留原拒绝原因作安全元数据并以脱敏请求ID关联告警/持久故障证据。具体降级介质、恢复及503语义待总协调/数据库确认，当前没有已实现的失败保障。

3. 成功任务更新、成功留痕必须同事务提交；后端不直接修改数据库模型/迁移。上述是已采用业务约束与待审接口提案的区分，不构成单方冻结契约。
