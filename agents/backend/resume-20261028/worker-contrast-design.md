# 同源7/16 worker配置对照：先定位排队，不改业务

后端AI设计，2026-10-28。依据是根协调器新公开的旧源935诊断汇总；该汇总不是将要测试的新DB审计修复源的性能证据。总协调明确选择先不扩Settings配置面；本岗不改产品、不上云。

## 假设与唯一变量

假设：每进程连接池的实际等待与同步handler前延迟，是当前400客户端短窗的重要已观测延迟段。把API worker从7改成16，可能减少单worker排队并允许更多独立进程推进I/O，但也可能使MySQL、磁盘或CPU竞争更重。结果未知，不以“核数够”预判成功。

第一对照只改变同一产品/镜像的worker数量7→16。保持原`t44.api:app`入口、完整验证/鉴权/两阶段UoW与锁/幂等/审计/outbox；每worker继续pool_size=5、max_overflow=10、timeout=10，HTTP线程限制、TLS/连接复用/客户端实现与记录方式不变。当前generation已支持7/16，无需新增产品配置或先改池。

## 相同输入与执行次序

1. 两臂绑定同一个新源SHA、依赖lock、镜像实件与配置摘要；从同一冻结seed/anchor准备独立但业务分布一致的任务、依赖、审查、容量、提醒资格与身份。两臂数据集和事件键分别独占，不能让后跑的一臂复用先跑的终态/幂等结果。仅顺序运行一个臂，停止原所属API后再切换，不能7+16并存争用。
2. 列出每个角色实际engine/pool数和MySQL max_connections及已用/保留预算。API理论上限从105到240；若实际max_connections=384，144是算术余量，尚未减其他角色和管理连接。预算不足或出现连接耗尽先停止，不盲增上限。
3. 两臂执行相同、另有标记的预热步骤；保留真实连接建立和worker覆盖率，不把更充分预热只给16臂。预热任务/提醒不得消耗计量独占样本。连接数增长和冷连接开销另记；没有实际确认全部进程热身就不声称“已全预热”。
4. 先40客户端检查，再400客户端执行同长度、同循环数与四操作混合的开发短窗。源、数据、时钟、记录和样本状态全部绑定。第一对7→16只是有方向性的配置证据；若要因果/稳定性更强且预算允许，应新数据做反向顺序16→7或另一对，而不是筛选最好的一轮。

## 收集与判断

每臂保留客户端各操作真实完整数、HTTP/传输错误、延迟原样与连接复用方式；服务端按真实request_id配对记录ingress/body-ready/sync-handler-start/end/send-end。同一请求可计算实际非重叠段，不能把多个P95相加或用客户端P95减服务P95算网络。

每worker记录实际处理量、活动线程/AnyIO token实际值与使用、线程提交至执行等待、池size/overflow/checkedout/等待；汇总不能仅给全局peak=15。收集MySQL连接、CPU、IO/提交与必要的项目内锁等待关系，完整连续资源流及结束尾部。SQLcursor墙时包含数据库/调度/I/O等，只有关联等待/语句或受控变化后才收窄根因。观察器自身写入/CPU/丢样也要记录，不通过关闭正式记录来做出更快的验收。

| 结果 | 可支持的下一步 | 不能宣称 |
| --- | --- | --- |
| 16臂池等待与handler前延迟下降，错误不升，各操作尾部稳定下降 | 在该同源环境采用16配置，并另做正式独立600秒运行 | 已修所有根因、旧935或新源已正式达标 |
| 池等待下降但cursor/提交等待上升，尾部未改善 | 检查DB服务/磁盘/锁与过量并发，必要时回退7 | 继续加worker/连接一定有效 |
| 单worker负载不均而平均资源不满 | 检查连接分配/keepalive及worker分布，不改业务门禁 | 任一worker峰值等于全机同时饱和 |
| 任一错误、连接耗尽、资源尾缺或数据/源不一致 | 保留原失败并停止该臂，修复前提后全新对照 | 删除错误样本或拼短窗作600秒通过 |

有界池配置暴露只留后续设计选项：必须先有新证据、总连接预算与单变量实验，默认保持5/10/10且不绕过持久层owner。此时没有补丁、没有候选测试，也没有预填通过。
