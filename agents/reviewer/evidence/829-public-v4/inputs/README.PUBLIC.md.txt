## v4 clock-only correction: 829-DEADLINE-UTC-01

The preserved v3 defect is reproduced with no socket: expiry UTC+10 seconds, monotonic fixed at 0, UTC moved forward by 20 seconds. Its controller started a fake request and returned HTTP 200 with `complete=true`. That failed boundary is retained as an explicit PUBLIC runtime reproduction; it is not SUT evidence. v4 changes only public time control and its selfchecks. No system clock, private business oracle, performance criterion or source under test is changed.

v4 checks actual UTC and monotonic at request admission, immediately before transport, during body steps, after transport close and immediately before returning. Either deadline rejects completion even when HTTP 200/full raw body was received. If UTC expires while the final response record is being persisted, a `request_completion_rejected` event invalidates that sequence and the returned result is incomplete. Raw status/headers/body remain available; a late success is never counted as a passing response. Both clock samples and the reason for expiry are recorded.

Each conversion uses one ordered `mono_before / UTC / mono_after` sample. The UTC remaining allowance is anchored to **mono_before**, and intersected with the original supervisor/wall deadline. Initialization or launch work cannot move the expiry later by taking a fresh `mono_now + old_remaining`. UTC moving backward does not extend the original monotonic cap.

The supervisor uses the same paired-clock helpers and continuously checks both clocks at a configured **0.01-second** polling interval; a monotonic timer remains an additional guard. The earlier observed UTC or monotonic expiry signals SIGKILL to the runner process group. Public receipt/status records include the conservative anchor, configured interval, actual sample count/max observed interval, first expiry observation, signal clock, observation-to-signal time, monotonic deadline lag and signal-to-process-exit-observation time. UTC overshoot after a wall-clock step is labeled separately: it is not falsely described as OS scheduling latency. Finite polling can miss a transient step that occurs and reverses between samples. Actual OS scheduling can delay polling/signaling/exit observation; no zero-delay or exact-kernel-exit guarantee is made. The actual recorded intervals/observations delimit the evidence.

RSS monitoring remains **one-second sampling of the single runner PID**; it is not process-group/descendant aggregate memory accounting. This limitation is deliberate and is not expanded into a new process-isolation design in this functional stage.

## Retained v3 control revisions

The controller ceiling is now 50,000,000 requests. A 400-client, 600-second closed-loop workload at 100 ms is approximately 2,400,000 steady requests; 30 seconds of excluded warmup adds approximately 120,000. A separate performance grant must state `run_kind: formal_candidate` and allow at least 3,000,000 requests; 50,000,000 is the technical maximum and a recommended request allowance where disk/time/resource scope permits. A smaller allowance is accepted only as an explicit diagnostic run. Any request, disk, response-size, RSS or deadline boundary exhaustion makes that run incomplete/diagnostic, never a completed formal performance group. There is no finite cap that can support an arbitrarily fast endpoint: reaching any cap is a proof limit, never a reason to shorten the required 600 seconds or discard failures. The 400/600/270 ms/1000 per minute criteria are unchanged.

Raw records are now losslessly zlib-compressed before encryption. `control.py` uses Apple's CommonCrypto AES-256-CBC/PKCS7 with random per-frame IVs and independently keyed HMAC-SHA256. Each frame authenticates its index, header, previous tag and ciphertext before decryption. A final streaming SHA-256/HMAC closes the file. Close/hash/recovery never call whole-file `read_bytes`. The technical limits are 64 GiB compressed content, 64 GiB actual ciphertext and 1 TiB uncompressed record safety space, independently lowered by the grant. Frame reservations prevent a disk-budget failure from partially writing the next frame. Every completed append is fsynced. Compression is lossless: request/response bodies, headers and transport errors are retained. Limits cannot be satisfied by stripping a body; an exceeded limit is an incomplete run.

The request timer caps connection, TLS, HTTP parsing and body reads at 30 seconds and by the run deadline; v4 additionally performs the actual UTC/monotonic dual checks described above. It actively shuts down the socket. Each body step checks the remaining total deadline; a late transport return is rejected. A timer alone cannot guarantee interruption of an uncooperative Python transport or blocking native operation, so `supervisor.PUBLIC.py` is required. It starts the runner in a new process group, supplies a receipt bound to the exact child/parent PID and frozen tool, and sends SIGKILL to that process group when the continuously sampled UTC expiry or original monotonic wall limit is observed, without an intentional post-expiry grace period. It also monitors runner RSS (default 4 GiB, hard technical ceiling 8 GiB). Actual enforcement time/lag is recorded publicly; this is an OS-enforced stop request, not a claim of mathematically zero scheduler latency. A hard stop or RSS stop is `HARD_STOP_INCOMPLETE_NOT_PROVEN`.

The journal durably records `request_begin` before network I/O. A socket wrapper records each TLS-decrypted HTTP wire chunk before the HTTP parser consumes it, including partial raw headers/body already received. Parsed headers and a full final body are also recorded where complete. If killed mid-request, the receiver can authenticate/decrypt the durable prefix with `recover_records`; a missing final manifest, truncated frame or missing request end never becomes a complete response. There is no need to rely on a graceful `finally` or encryption child flushing its pipe. Keys are 64 fresh random bytes, mode 0600 under private/secrets; no credential appears in command arguments, environment values, public records or ordinary summaries.
