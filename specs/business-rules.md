## 人员及数据范围

每个项目分项目经理、开发人员、评审人员。用户只能访问自己参与的项目；管理身份不自动允许读取未加入项目。项目经理管理成员与排期，批准发布和回滚；开发人员推进负责的任务；评审人员给出带证据的评审。实际操作者、决定者、时间和版本保留，AI不代替项目经理拍板实际回滚。

## 状态出口

默认正常流程：待受理→开发中→待评审→待上线→已交付。已交付不是删除记录；项目经理批准回滚时转已回滚。

| 当前状态 | 允许操作及前置条件 |
| --- | --- |
| 待受理 | 依赖全部已交付才可开始开发；也可记录阻塞 |
| 开发中 | 可提交评审，或记录阻塞 |
| 阻塞 | 必填原因、责任环节并保存阻塞前状态；解除需依据，回到阻塞前状态；回到开发中仍检查依赖 |
| 待评审 | 有证据的通过评审后进入待上线；不通过退开发中；可记录评审环节阻塞 |
| 待上线 | 四视角风险及回滚预案已评审后，由经理交付；也可记录上线环节阻塞 |
| 已交付 | 经理记录回滚原因、影响、目标版本、预案与决定后进入已回滚 |
| 已回滚 | 可查询完整历史；重新开发须经理明确新排期与返工决定，再检查依赖后进入开发中 |

除表中出口和解除阻塞返回外，其他迁移一律拒绝。任务状态字段无通用直接修改接口。依赖只在对方已交付时视为满足；创建/修改依赖拒绝自依赖和环，不能悄悄改变其他任务现状。

## 重试与并发

先鉴权及项目权限，再验证请求。同一用户、接口和幂等键的相同请求返回原操作结果，先识别重放再检查任务旧版本，不能把成功重试误判409。相同键不同内容拒绝。不同键持同一任务版本竞争，只允许一次更新，另一次409且任务不被改变。

成功的任务变更与成功审计同一事务提交。拒绝记录必须能够持久化，不能随失败主事务回滚消失。重放结果是原操作快照，前端应再查询最新状态，不把历史响应误当现在的任务版本。

## 延期升级默认值

扫描所有未交付、未回滚任务，阻塞不暂停计时。每60秒扫描，时刻用UTC保存、页面用北京时间显示。

| 级别 | 触发条件 | 收件人 |
| --- | --- | --- |
| 临期 | 距计划结束不超过24小时，尚未超期 | 责任人 |
| 超期 | 已超过计划结束，未满24小时 | 责任人和项目经理 |
| 严重超期 | 超期至少24小时 | 责任人和项目经理 |

首次发现已跨多个级别时只创建当前最高级别事件，不补发低级别轰炸。同一任务、同一排期版本、同一升级级别只创建一次；改期保留前后差异并开启新排期版本，规则调整记录版本和拍板人。阈值和清单集中配置。

业务事务持久化事件与待发送记录，MQ确认投递、消费后确认；通知按事件与收件人去重。MQ故障时转有标记的站内待办，同事件恢复后不再次提醒；新事件恢复正常投递。已读和已处理分别记录，不能把阅读当作问题解决。

## 评审与发布

项目评审采用reviewer岗位制定的八段式与十项清单。每个必需项必须有证据位置；缺证据不得通过。评审、上线风险与预案均带版本；计划、规则和模板改变留下原值、新值、生效时间、影响范围及决定者。
