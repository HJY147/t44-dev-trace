# UI002：人力保护拒绝的业务解释

## 依据与边界

独立v2固定4c的已公开容量/依赖界面报告确认：移除仍负责待受理任务的人员工时得到422 CAPACITY_REFERENCE_INVALID，数据/版本保护成功，但表单只有通用字段提示。缺工时的创建、转派、返工及成员使用保护提示也缺少可执行解释。Issue27处理这一前端可用性缺陷，不改后端、HTTP状态、冻结错误码、优先级或保护规则。UI003历史理由出口另由Issue28设计，不混入本阶段。

D005/D006及冻结v1.1明确：任务创建/允许状态转派须有效开发成员且在当前迭代登记工时；新迭代人力必须保留全部状态1–5任务负责人，状态6/7可移出工时；7返工先恢复有效开发身份和工时。项目成员/开发角色保护仍包括1–5和7。不能将“允许移出工时”解释为“允许移除成员”，不能建议在已开发状态直接转派。

## 最小解释规则

只有HTTP状态、服务器code、实际操作和必要表单schema同时匹配，才展示特定业务原因与下一步。不能仅凭422、英文message或当前可见20条任务猜原因/负责人。

| 状态/code与上下文 | 中文解释及下一步 |
| --- | --- |
| 422 CAPACITY_REFERENCE_INVALID / createIteration | 核对每个人都是本项目有效开发成员，每人仅登记一次有效工时；不声称已有活动任务或工时总量不足。 |
| 同码 / changeIteration | 迭代人力须保留待受理、开发中、阻塞、待评审、待上线任务负责人工时，同时人员有效且不重复。若正移除活动负责人，请先保留；只有允许转派状态才能合法转给已登记人员，其他任务先完成流程。已交付/已回滚可移出工时，成员身份另受保护。该码多因共用，不能断言一定只缺某人。 |
| 同码 / createTask | 负责人未登记在所选迭代工时中；先在迭代排期补登记，再返回创建。有效开发身份已由此操作的前置守卫检查，不把它说成工时预算不足。 |
| 同码 / changeTaskAssignment | 接手人未登记在任务当前迭代工时中；先补人力安排，再在原允许转派状态操作。 |
| 同码 / transitionTask + ReworkTransition | 返工前原负责人须有效开发成员且已登记当前迭代工时；先核项目角色、补回工时，再决定返工。不映射其他流转表单。 |
| 422 OWNER_NOT_PROJECT_DEVELOPER / createTask或changeTaskAssignment | 该负责人不是本项目有效开发成员；在项目空间核对成员及开发角色，再登记迭代工时后执行。 |
| 409 MEMBER_IN_USE / changeProjectMember或removeProjectMember | 仍负责未结项或已回滚任务，不能移除或撤销开发角色；保留身份，按允许状态合法处理任务。回滚任务可移出工时但仍保留成员/开发角色。 |

已知业务守卫拒绝以“人力安排不符合要求”或“成员仍有关联任务”为标题，给出上述解释，不再把它当普通字段格式错误。保留原输入、原始error.detail及追踪编号；不凭前端消息自动重试、改版本、转派、修改角色或数据。普通PARAMETER_INVALID/字段violations仍走原字段提示；未知code/不匹配操作/不匹配HTTP状态用原安全通用退路。网络、503、会话401、客户端SESSION_CHANGED、幂等重放和当前409刷新/版本采用语义保持。
