# UI003：计划历史理由的前端呈现

依据：Issue28、已准入5e8设计及records/decisions/plan-history-reason-implementation-admission.json。该准入是技术实现决定，不是学生亲自修改或独立验收通过。前端从root3f59d88单独新分支实施；后端候选和隔离环境未交付前只做组件夹具，不以旧API冒充新出口。

## 输入与输出

读取现有AuditEvent，唯一理由位置为after[]中field='reason'的条目，不添加reason_status、顶层字段或HTTP码。恰一个条目且value为非空白、≤2000 Unicode字符的字符串，才可标为唯一可核对的理由。保持原字符串，不trim；其显示标题为“原因与决定依据”，直接以文本节点呈现，不经过通用日期/operationLabels/display或HTML解释。前后计划、actor/time、evidence等仍按原记录显示。

多个reason（包括一个合法加一个非法、相同内容重复）不能任选或合并为唯一值。原始条目可以按“原始理由条目（未核对）”纯文本保留；缺失/空白/非法/超限不制造替代理由，不截断来伪装合法。不得改传入记录或排序/分页。

没有唯一合法理由时，只在outcome=1的成功changeTaskPlan、成功changeIteration（项目总历史）及明确before.state唯一'7'→after.state唯一'2'的成功transitionTask记录旁提示：“此历史记录未提供可核对的变更理由”。未成功、非计划、缺状态/重复状态等无法识别返工的残缺transition均不猜、不加泛滥警告。任务页原task_id过滤保持，迭代理由不变成任务改期理由。

## 实现与边界

增加小型纯展示判定函数，RecordView识别整条审计后增加中文理由区，并从其通用after显示副本移除已单独显示的唯一条目；不改原after。未核对原始reason条目也绕过通用格式化，避免日期开头抛错或操作名被翻译。该规则不改变普通字段的时间格式、业务表单、API客户端/session/R1、UI002映射或冻结14文件。

先用既有983真实组件在旧源证明中文标题/原文/缺失提示的红，再最小改码；覆盖2000字及Unicode边界、换行/空格、HTML样式、ISO日期、操作名字符串、重复/非法及缺失范围。最终新前端完整检查一次并构建，保留旧测试和所有原失败。
