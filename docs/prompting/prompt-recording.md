# 提示词与 AI 协作记录规范

版本：prompt-recording-v1；适用阶段：初始化及后续真实开发留痕。
维护岗：prompt_engineering；共享台账的登记和汇总由总协调调度，本轮不修改 `records/prompts/ledger.jsonl`。

## 基本依据与边界

- 原始用户输入原样保留。优化稿另存，逐项解释修改，不覆盖原文，不自动视为用户审定。
- 提示词是输入证据；任务完成、代码实现、测试通过还须各自产物和运行证据，不能互相替代。
- 当前 U001-O1 是建议稿；`ROLE-prompt_engineering-BOOTSTRAP-v1` 是本轮实际使用的岗位派工。两者不得合并为一次“已使用优化 prompt”。
- 从收到时开始记录真实过程，不重建不存在的历史，不补造版本、人工改码、幻觉或截图。
- 独立测试岗不接收本目录的开发提示词记录。测试中性输入由总协调另行准备；本岗不与独立测试实例通信。

## 文件与标识

| 资料 | 命名或标识 | 含义 |
| --- | --- | --- |
| 用户原文 | `U001-original.md` | 不可覆盖的输入来源。后续新输入另分配 ID。 |
| 优化稿 | `U001-optimized.md`，内部版本 `U001-O1` | 文本提案，使用状态独立记录。后续修订保留先前快照。 |
| 修改说明 | `U001-changes.md` | 原句、改句、理由、范围及尚未确认事项。 |
| 实际岗位派工 | `ROLE-<role>-<task>-v<n>.md` | 原样保存收到或发送的实际正文，关联任务文件。 |
| 真实演进链 | 每链独立 `lineage_id` 和版本 ID | 同一目标经实际反馈、修订、再次使用形成的连续版本。 |
| 上下文映射、人工修改、幻觉、规则变更 | 各自独立事件 ID | 不用同一条记录冒充多个不同性质的事实。 |

本轮实际派工原文已存 `records/prompts/ROLE-prompt_engineering-BOOTSTRAP-v1.md`。命名建议适用于后续新文件；本轮不替其他岗位追补未收到的消息。

## 提示词台账字段

共享台账使用 JSONL，每行一个真实事件。下表是后续登记字段约定；尚无事实的字段填 `null` 或空数组并解释，不能把待办写成已发生。

| 字段 | 取值与用途 |
| --- | --- |
| `id`、`lineage_id`、`version` | 唯一事件标识、真实演进链与链内版本；单独岗位分叉另立链。 |
| `at`、`operator`、`decision_maker` | 带时区时间、实际操作者、实际决定者；AI 与用户分别标识。 |
| `origin`、`kind` | 来源为 user / coordinator_ai / role_ai；类别为 original / optimization / dispatch / revision 等。 |
| `parent_refs`、`derived_from` | 修订父版本和来源；只表示关联时不得写成前后演进。 |
| `path`、`content_sha256` | 原文或快照位置与摘要，确保后续能核对实际文本。 |
| `context_refs` | 实际提供的需求、规则、接口、文件版本或 commit；每项记路径与版本或摘要。 |
| `change_reason`、`change_refs` | 具体问题或反馈与修改说明位置；不写“优化一下”代替依据。 |
| `status`、`used_at`、`execution_ref` | received / proposed / used / superseded；只有真派工或真调用才写 used，并给实际使用证据。 |
| `artifact_refs`、`result_refs` | 真实产物版本、命令输出、验证结果；未运行明确标注。 |
| `human_code_edit`、`human_edit_refs` | 用户亲自修改代码的事实与差异；AI 改码或用户仅同意时必须为 false。 |
| `verification`、`unverified` | 自查、模块自测、集成验证、独立验收分别记，列明未验证项。 |
| `visibility` | 默认开发内部；发给独立测试的资料须经总协调另行构成中性上下文。 |

已有简版台账记录无需凭空补出缺失历史。总协调可按真实证据增加登记事件或迁移字段，保留原记录及迁移依据。

## 真实版本演进

1. 保存第一版实际输入与上下文，说明目标和边界。
2. 保存这次执行产生的实际产物和反馈；没有执行时只能记为建议稿。
3. 根据具体反馈修订，保存变更理由与前后文本或差异。
4. 真正再次发送或调用后登记使用证据，再记录新的实际结果。
5. 同一目标下的重复改进可计入演进链；只换岗位名、格式或拆成多个角色不算真实演进。

任务书 AC-09 要求提示词演进至少六个版本。验收汇总时逐版核对文本、上下文、实际使用和改进依据，不能把 U001 原文、未使用的优化稿、十个岗位初始化文件直接相加凑数。本轮只建立规范，不声称已达到六版。

## 上下文到最终代码的映射

后续每条映射至少包含 `mapping_id`、实际 prompt ID、上下文文件及版本、代码文件/符号及 commit、生成内容摘要、实际修改者、修改前后差异、修改原因和验证证据。代码不存在或未冻结时标为待建立。

任务书专属要求至少五处映射，并逐处说明人工改了什么、为什么。AI 自动修订须如实标为 AI；用户审定与用户实际改码分别记录。最终代码版本变化时重新核对映射，避免指向已失效的行号。本轮没有业务代码，不生成虚假的五处映射。

## 人工修改对照

每条至少保存 `human_edit_id`、用户本人操作的依据、原 prompt、修改前代码、修改后代码或 diff、文件与版本、修改原因、时间和验证结果。无法确认作者的差异列为待确认，不纳入人工修改完成数。

任务书 AC-09 要求至少十二条人工修改对照；AI 代用户修改、AI 生成文案、用户口头同意和同一 diff 的重复切片均不自动计入。用户亲自修改的事实必须由实际操作或其明确提供的事实支持。本轮实际修改者是 AI，人工代码修改计数为零。

## 幻觉与不可行建议

每条至少保存 `hallucination_id`、原 prompt 与上下文、AI 原始建议的原文证据、为何不实或不可行的可核查依据、实际识别者、识别时间、纠正动作和验证结果。区分不实事实、不可行方案、待确认风险和普通实现缺陷，不把假设风险包装成已发生幻觉。

任务书要求至少三条真实幻觉及人工识别与纠正过程。任务书举例只是示例，不能抄作本项目发生记录；AI 自己发现的问题不能改写成用户发现。本轮尚无可登记的真实幻觉，不虚构三条。

## 规范变更与人机决策

每次调整环节模板、字段规范或升级线，保存 `rule_change_id`、规则位置、原值、新值、生效时间、影响范围、拍板人、理由和验证/迁移情况。候选方案与生效决定分开记录。

状态出口与结项口径、字段规范与错误码取舍、是否执行回滚等判断须保存实际决定者。AI 可整理依据和提出建议；未经用户实际审定不得标为用户决定。本岗不替相关责任岗冻结业务规则。

## 岗位提交与汇总

每岗在交接单 `prompt_refs` 提交实际 prompt ID、任务文件、原文或快照位置、使用状态、产物及结果引用。文档岗从已归档事实中汇总，不改写作者身份，不以“AI 说完成”作为验证证据。

提示词岗整理后交总协调登记；跨岗来源不足时只记待补项，不替其他岗位构造提示词。不得把用户口令、Token、私钥或云凭据写入上下文快照和日志；如需环境说明，只记录无密值的字段名及取值来源。
