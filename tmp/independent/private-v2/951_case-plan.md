## Classification and gates

Each assertion records case ID, frozen precondition, actual setup response, request ID, HTTP result/schema, before/after task/iteration/member snapshots, independent read-only SQL where needed, timing, evidence hash, exact product/harness/environment SHA and outcome. PASS requires the stated condition was reached and every observable assertion passed. FAIL requires a reached valid precondition and a conflicting SUT observation. BLOCKED means a needed neutral capability is missing; NOT_RUN means not attempted. SPEC_AMBIGUITY records conflicting/under-specified authority without choosing a product-friendly interpretation. UNREACHABLE_BY_PUBLIC_API identifies an error branch whose precondition cannot be legally manufactured. SETUP_FAILED is separate from the scenario under test and may itself establish a setup contract defect. Harness faults are recorded distinctly and do not become SUT failures. Any untested mandatory acceptance item prevents an overall pass. A retry never erases a failed attempt.

Phases: (A) frozen cases only; (B) bind exact SUT/environment, verify neutral capabilities, API blackbox + read-only storage + browser; (C) constrained fault/MQ/scheduler/transaction observation; (D) formal data/performance; (E) separately authorized whitebox/CI/coverage/source-size/artifact audit. No whitebox is authorized by this plan. Operational controls and account setup are synthetic-only. Runtime project-manager decisions are synthetic test records made by AI under the acceptance fixture, not the student's actual production release/rollback approval or human modification.

## Known specification uncertainty (frozen, not a product defect)

The frozen OpenAPI ContractValidationResult.schema_version constant remains1.0.0 while API info/Meta are1.1.0. Runtime response must match frozen Schema1.0.0; this is logged as specification-version ambiguity, not silently changed to1.1.0. createTask advertises self-reference/cycle errors although a new server-assigned task has no publicly creatable predecessor referencing its not-yet-existing ID. Those branches are UNREACHABLE_BY_PUBLIC_API absent a neutral valid fixture proving reachability; we do not corrupt DB or guess future auto-increment IDs to force them. After rescheduling, an old assessment simultaneously lacks current baseline and current approval; absent a specified priority, the assertion is refusal with a declared baseline/approval code and both conditions are recorded, not a fabricated exact-priority failure. General INTERNAL_ERROR cannot be guaranteed by valid public input; neutral fault/whitebox trigger authorization is required. Transaction-uncertain and audit-only outage require selective commit/connection control beyond whole-service stop. These gaps block branch-completeness claims, not every independent functional case.
