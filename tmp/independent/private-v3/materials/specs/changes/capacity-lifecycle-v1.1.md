# 迭代人力生命周期 v1.1 变更提案

状态：D005及D006业务选择已采用；以下技术细化待限定审查，尚未修改或重新冻结v1契约。父基线为ae60dc3冻结1.0.0及records/spec-freezes/v1.json的11个摘要。实现依据与本人选择分开记录。

## 需求和范围

任务转派前，接手人必须是本项目有效developer，且存在于任务所属迭代的有效capacity记录。改迭代计划时，新capacity必须继续包含该迭代全部未结项任务负责人。先补人力安排，再转派；先转走允许转派的任务或结束当前周期，再移除产能人员。D002禁止开发后转派的边界不变，不增加预算耗尽或自动平衡算法。

迭代工时保护按D005/D006明确：状态1至5的任务负责人必须保留，6已交付、7已回滚可移出；7返工进入2前必须补回有效人力并核对当前capacity。项目成员/开发角色移除的既有保护仍包括1至5及7，不随本次工时规则放宽。原稿把两套保护混同，审核指出后已更正；不把该AI纠错计为学生识别。

## 接口与数据变更

| 操作 | 拟定行为及错误 |
| --- | --- |
| createTask | 保留IAT02修复：负责人匹配capacity；已有CAPACITY_REFERENCE_INVALID，不新增错误码 |
| changeTaskAssignment | 保留原角色、允许状态、CAS和幂等重放先后；目标负责人有效developer检查后，检查当前迭代capacity。新增该操作422 CAPACITY_REFERENCE_INVALID分支 |
| changeIteration | 保留现有有效成员/唯一容量项检查；新capacity缺少任何状态1至5任务负责人时422 CAPACITY_REFERENCE_INVALID，计划、plan_version和排期差异均不写入 |
| transitionTask action9 rework | 保留原经理、返工/排期/依赖证明及版本守卫；恢复开发前核对当前有效人力，缺失时422 CAPACITY_REFERENCE_INVALID，不改task/cycle/decision/diff |

API路径仍/api/v1；契约信息版本拟为1.1.0，同时更新info.version与Meta.contract_version.const，保持二者相等。全局已有CAPACITY_REFERENCE_INVALID保持原数值，仅扩展上述操作的声明分支及描述；不添加表列、不放宽字段类型、不改变状态出口。权威specs/contracts/openapi.json及backend/t44/contracts/openapi.json运行副本/元数据/说明须同步；前端直接导入权威源，无另藏第三份手写契约，相关fixture/版本断言须核对，旧1.0.0内容通过父冻结提交及原摘要可恢复；新版本单独清单、记录父版本与差异，再派新无历史实例验收。

## 并发与事务设计

changeTaskAssignment加入已有项目行锁集合。createTask、changeIteration和rework已在同一项目锁保护下；统一会话/幂等→项目→有序成员→有序任务的锁序，防止检查产能后被另一个事务移除人员。changeIteration在已有项目事务中核对所属迭代任务，不能另开事务提前提交或只靠前端选项约束。

成功仍与审计/outbox/幂等快照同事务，拒绝仍在回滚后独立审计，旧成功请求的重放不重复执行新增守卫。失败不推进版本，公开错误不得暴露跨项目内容。

## 验证准入

- 未登记接手人拒绝且task版本/owner不变；登记后合法待受理转派成功，原允许状态边界不变。
- 状态1至5负责人不可移出capacity；处理允许转派的任务或进入6/7后可移除，其他人员可独立调整。
- 终态人员被移除后返工拒绝；补回有效人力后按原证明、版本和依赖条件返工成功。
- 移除拟接手人/创建负责人/返工负责人的容量与相应动作竞争时，一方成功后另一方须按最新人力状态拒绝；不得出现已激活任务负责人缺产能的提交后状态。先合法转派、再移除原负责人可以依次都成功，不把不同资源的所有安全更新一概限制为仅一次成功。
- 成功/拒绝审计、版本、幂等、已有38操作契约和真实MySQL回归继续验证；旧v1独立报告不覆盖，新功能不声称已有独立测试。

技术审核须先确认范围、状态解释、错误分支和锁序；之后才修改权威OpenAPI及运行副本并记录新的冻结清单。不能为了让新测试通过而回写旧冻结摘要或旧验收结果。
