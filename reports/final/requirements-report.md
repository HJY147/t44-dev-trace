## 2. 背景、目标和范围

中小软件外包团队需要把接口、字段、任务依赖、代码评审、上线风险与责任决定集中留痕，重点解决阻塞不透明、延期发现晚、回滚无法追责的问题。成功标准是合法路径可执行、非法及并发路径被拒绝且可追溯；不能只展示可编辑状态列表。

系统为浏览器前端、业务后端、单机关系库、消息队列和定时调度组成的前后端分离单体分层系统。不做业务微服务、集群、多地域或通用云部署平台。产品中的发布/回滚是流程评估及人类决定记录；项目自己的镜像发布、备份恢复另由运维配置承担。AI留痕不要求运行时调用在线大模型。

## 4. 主要成功与拒绝路径

| 场景 | 成功路径 | 必须保持的失败行为 |
| --- | --- | --- |
| 创建与开始任务 | 合法成员登记任务/计划/容量；负责人且依赖全部已交付后开始 | 无资格、跨项目引用、依赖未满足拒绝；不能先改状态后补日志 |
| 阻塞和解除 | 保存阻塞前状态、原因、责任环节；凭解除依据返回原状态 | 不接受客户端任意指定返回状态；回开发须重新检查依赖 |
| 评审与交付 | 固定审核SHA及当前轮次，证据完整通过；当前排期/交付轮次的风险预案获审，经理决定交付 | 自审、缺证据、旧SHA/轮次、未审预案、越权或越级拒绝 |
| 回滚与返工 | 经理记录原因、影响、目标版本、已审预案；返工建立新计划和交付轮次 | 不删除任务冒充回滚；不得沿用上一交付/评审轮次的批准 |
| 并发与重试 | 同键同内容重放原快照；不同键同版本竞争只一成功 | 同键异内容409；原快照不冒充最新状态；拒绝不改任务；提交不确定返回503并保留原键 |
| 升级与故障 | 只选当前最高档，持久事件和计数同事务；MQ投递/消费或降级待办 | 不截断全部有效收件人；重复扫描/消息不增加次数，不清空已读/处理；202不是送达 |

七状态的业务顺序和例外出口以business-rules v1为准；不能从“待受理—开发中—阻塞……”的文字排列推断所有相邻迁移合法。任务状态无通用PATCH接口。已读与已处理独立，处理通知不等于解除阻塞。

### 4.1 接口与错误表达（待Q002采用及冻结）

三类代表入口为`POST /projects/{project_id}/tasks`、`POST .../tasks/{task_id}/transitions`、`POST .../release-assessments`及其评审/交付动作，完整路由见[契约说明](../../specs/contracts/README.md)。部署保留同源`/api/v1`前缀。

| 结果类 | 技术提案 | 用户可理解的处理 |
| --- | --- | --- |
| 格式/字段/证据错误 | 400/422 | 指明可修正字段，保留非敏感输入，不回显Token/口令/原SQL |
| 身份/项目/动作不允许 | 401/403 | 重新登录或停止该动作；不返回其他项目详情 |
| 授权范围内资源不存在 | 404 | 提示资源不存在并返回安全上下文 |
| 状态/版本/依赖/幂等冲突 | 409 | 保留草稿、取服务器最新状态；不能自动换键覆盖他人操作 |
| 请求过大/登录过快 | 413/429 | 统一错误体，必要时给Retry-After；非HTML成功页 |
| 必需存储/拒绝审计失败或提交不确定 | 503 | 不宣称已提交/已审计；沿用原幂等键恢复，运维留脱敏故障证据 |
| 升级可靠受理 | 202 | 事件/outbox已提交；消息实际送达另行观测和验证 |
