# V4 发压器有界本机校准：公开摘要

本次只有一次本机 stub 校准，**没有接触任一 SUT，也没有新发正式 CI 请求**。原 H2 三入口、共享 driver 和判据保持。独立父进程墙钟 33.410 秒，client 整体存活 33.087 秒，均在事前界限内；client/stub 均 exit0，两个自有子进程已回收。

400 用户的即时/50ms 响应场景仍观察到客户端数秒循环延迟、超时与未到达 stub parser 的调用，证明本机隔离测试路径本身能够出现这些现象。它**不能证明原 Linux CI 的同一原因、不能修复原 H2 测量有效性、不能归因或排名 S1/S2**。

## 事前冻结与隔离

- 授权中性文件提交：`027d759853a88a756735b0aa1ee0f786e53b3e91`。
- 校准方法/工具冻结 F：`7795ed08327cfdee09db51707056a0d89678590e`；随后公开元数据 M：`fe9dc6de1ea84e23ee4e2aa5de71bdffff98f92c`。分支 `codex/independent-calibration-v4`。元数据已先发表，再运行。
- 原 H2：`fc75ca7d092517f597c8931d9e8d11b646e441b7`。不执行 H2 模块、Driver 初始化、fixture 或 control；只从该冻结 tester 文件 AST 提取原 Evidence、key、validate_response、request、sampler。共享文件 SHA256 `40136e5d8fb152cbbfa35cca2fb489e1fa82503e8524c6b0f60d945395b31c65` 在运行前核对。
- 一个 supervisor 创建独立 client 进程和独立 asyncio stub 进程，stub 仅绑定自己申请的 `127.0.0.1:0` 临时端口；端口/PID 不公开。未查找、连接或清理既有项目监听/进程，没有 app/DB/MQ/scanner/账号访问。
- 四场景各一次。调度上限合计 27 秒，调用预留总上限 6800；另有父进程 55 秒 client 全寿命界限与 150 秒自身 alarm（均严格小于授权的 60/180 秒）。只通过本次 Popen 句柄终止和回收自有孩子，不使用广义 kill。未触发硬限，没有加测或重跑。

|---|---:|---:|---:|---:|---:|
| small_immediate | 4 | 4 | 1000 | 0 | 0.487 |
| large_immediate | 400 | 8 | 2500 | 0 | 10.503 |
| large_bounded_delay | 400 | 8 | 2500 | 0.05 | 10.885 |

4 用户即时场景先到 1000 调用上限，实际约 0.487 秒，并未声称跑满 4 秒；其余场景包含窗口结束后已有调用排空。全 client 寿命也低于 60 秒，故实际负载总墙钟不超过该界限。

| 场景 | client 记录调用/返回 | client 成功/超时 | stub 收到/写回复 | client P95/max ms | 实际短窗内成功 |
|---|---:|---:|---:|---:|---:|
| small_immediate | 1000/1000 | 1000/0 | 1000/1000 | 1.955/13.375 | 1000 |
| large_immediate | 1021/1021 | 625/396 | 654/654 | 6322.557/7084.110 | 373 |
| large_bounded_delay | 989/989 | 588/401 | 619/619 | 6522.158/7904.048 | 372 |
| large_timeout_boundary | 800/800 | 0/800 | 800/800 | 5143.795/5148.115 | 0 |

合计 client 记录 3810 次调用：成功 2213、超时 1597；stub 解析收到 3073 次并写回复 3073 次。记录调用不是独立的线上 HTTP 发出证明；少于 client 记录数的 parser 计数保持真实差异，未补成“所有请求都到达服务器”。TCP 建连/监听 backlog、包传输及宿主调度的独立归因未知。

stub 收到后到写回复的 P95 分别约 0.0145、0.0224、51.3935、5205.2180ms；最大值分别约 0.4356、0.0471、52.0930、5207.4557ms。这段计时不包含请求到达 parser 以前的排队/传输。socket 写入成功也不证明 client 已读到回复。

5.2 秒场景故意跨过原 5 秒 async budget，800 次调用均超时，实际超时 elapsed 为 5000.145–5148.115ms。即时/50ms 场景的超时最大 elapsed 分别 7084.110/7904.048ms，保留真实墙钟，不裁剪为 5000ms，也不把它当作 stub 业务处理时间。

原 Evidence 的完成计数使用硬编码 600 秒窗口。本次短场景没有借用它来宣布吞吐：旁证单独序列化 trace origin 与实际阶段 deadline，从逐请求记录重算短窗成功。400 即时/50ms 场景共有成功 625/588，其中实际 8 秒窗内为 373/372，其余为排空完成。没有套用 H2 的 judge、270ms 或每分钟1000门槛。

client 保留原每秒 sampler、gzip trace/事件写入、响应元信息断言和完整 schema 校验：成功响应到达该步骤后均完成校验，共 2213；超时场景无响应可校验。HTTPx 仍为连接/keepalive 上限 800、5 秒 async timeout。周期完整 elapsed 与 HTTP elapsed 另列 JSON；未单独剥离 schema、gzip、采样器或连接管理的 CPU 成本，所以不声称已定位某个函数为唯一原因。

独立 stub 每 100ms 采样，共 328 个样本，最大额外循环延迟 0.002617s；进程 CPU 共约 0.396s，RSS 生命周期高水位 36110336 bytes。活跃请求从完整 body 被 parser 接收到写回复结束计数；即时场景峰值1反映该区间很短，不等于 TCP 连接只有1。5.2 秒场景峰值800表明前一轮 client 超时后，stub 的旧请求仍可与后续调用重叠；400逻辑用户不能直接等同于服务端始终400活跃执行。

本机为 macOS/arm64、Python3.12.10、httpx0.28.1、jsonschema4.23.0。macOS getrusage 的 RSS 原单位为 bytes，且为进程生命周期高水位，不是每场景独占峰值；原 sampler 字段名 max_rss_linux_kib 在本机并不代表 KiB，公开表已按实际平台解释。Linux H2 的单位没有被改写。`/proc/meminfo` 在本机不可用，保留 unknown；未额外盘点机器 CPU/内存、kernel 传输或 CI 硬件等价性。

## 保留的准备失败与证据限制

- 初次依赖安装因系统证书链校验失败；使用已有本机 certifi CA bundle 后成功，未关闭 TLS 校验。准备阶段访问过包索引，不是校准 HTTP 或 SUT 请求。
- 冻结的依赖 inventory 命令误解析了 venv Python 符号链接，实际列出基础解释器的 pip，**未正确冻结完整传递依赖清单**。事前指定的 httpx/jsonschema 版本与运行进程回报相符；完整实际 venv 依赖已在运行后只读补录到公开 JSON，不能宣称它们全部事前冻结。F 原件不改写。
- 初次添加新私密文件被 ignored 路径规则拒绝，随后仅对授权的三个新冻结文件显式添加，F 形成后才执行负载。未把准备失败写成正式测量。
- 原始压缩 trace 已核 hash、逐组请求/失败/状态与 P95/max；stub 事件数与其独立汇总对齐，源 H2 与新 F 字节校验保留。private 原始输出、工具、内部方法和日志不发表。
- 只有一轮短时、固定小响应形状的本机校准，没有完整业务请求生成、fixture、负例 oracle、写后恢复、600秒稳态、消息或通知验证；没有独立 packet capture。不能从本机结果补出原 CI 的真实网络并发或唯一瓶颈。

本轮有限结论：隔离 tester 路径在本机 400 用户条件下已观察到调度/超时限制，原 H2 仍没有有效 400 并发性能通过证据。两份 SUT 的产品性能结论继续不确定；不追加测试、不排名，也不冒充整体作业验收。
