# Independent benchmark 772-v1 (frozen 2026-10-29)

This is a newly defined independent benchmark. No earlier protocol, result or conclusion is replaced. Only the original T44 docx, specs/requirements.md, specs/business-rules.md and specs/contracts/openapi.json supplied on 2026-10-29 informed the cases. The supplied OpenAPI advertises version 1.2.0 and draft status; matching this snapshot does not silently certify a formal specification freeze.

## Workload and metric gates

One indivisible cohort: 400 persistent closed-loop clients, no think time, no request retries, no login, no replacement round. Each client exclusively owns one mutable task and one separate escalation task. Fixed repeating order: GET authoritative mutable task; successful real block; valid contract validation of an unblock candidate; successful real unblock; escalation API with a fresh idempotency key. Request mix is query 20%, state transition 40%, contract validation 20%, escalation API 20%. Partial last loops are counted exactly. These are 400 continuously active logical clients; in-flight requests and client-side gaps are additionally reported, never renamed as 400 simultaneous sockets.

The 400 clients enter a common barrier. At least 60 monotonic seconds of warmup are followed by a fresh, contiguous, full 600-second steady period. Completion throughput is reported in ten nonoverlapping steady 60-second buckets; each must complete at least 1000 requests. Zero business, HTTP, transport, response-contract and assertion errors is required. All four request classes independently require nearest-rank P95 <= 270 milliseconds, measured from before connection/request work until the complete HTTP response is read. Failed requests remain in evidence and latency statistics. Steady latency cohort uses requests STARTED inside the steady interval, including bounded drain responses; throughput counts their COMPLETION inside each minute. Warmup and pre/post checks never count towards the 600 seconds. No short windows are joined. Empty groups and incomplete coverage are NP, never 0 or PASS.

Escalation steady workload targets existing current-level business events and tests the real authenticated, version-checked, rule-checked, deduplicating API. created=true and created=false counts and latencies are separate. Repeated existing-event calls are not new MQ event throughput. 202 only proves the API's accepted result. Recipient/event uniqueness, actual delivery/fallback and transaction/audit postconditions are separate from the four latency metrics. Missing independently observable postconditions are NOT_OBSERVED and prevent a complete independent acceptance conclusion, even if latency gates pass.

## Inputs and privacy

Public inputs contain only origin, address/TLS binding, time window, immutable identity digests, fixture quantity summary and filenames. Real tokens, role identities, project memberships, inventory IDs/current versions/events and business assertions are private on LOAD, transmitted in an opaque authenticated capsule or directly through the designated encrypted transport. Root may copy/hash opaque files but must not inspect PRIVATE files or keys. No developer diagnostic package or old result is an input.

Minimum inventory: 400 exclusive developing tasks, owned by the supplied developer, all dependencies currently delivered, with plan end more than 24 hours beyond the grant end; and 400 separate live tasks each with an existing current highest-level escalation event and neutral event/schedule/version/recipient snapshots. Tasks span approximately 40 projects; overall fixture approximately 6000 tasks/9000 dependencies/15000 reviews+decisions. No independent claim about those counts is made from a producer declaration alone. Four actual roles are manager/developer/reviewer/escalation service; either four existing sessions or explicitly authorized one-time credential preparation occurs outside the tester. The tester never creates or extends sessions. Each actual expiry must cover the entire NEW grant window including warmup, steady, drain and postchecks. No old 600-second session/packet lifetime is inherited.

## Finite execution

A single explicit default-false grant binds run ID, created UTC, absolute start/end UTC, allowed origin, exact runtime/source/fixture/OpenAPI identities and resource limits. It is consumed once with exclusive creation of a receipt. Linux AMD64/Python 3.12 preflight and the SUT run are one granted invocation. No remote preflight or cloud action is permitted beforehand. Exact source-free image digest is supplied later. Required hard ceilings: 8 CPU, 8 GiB RAM, 2048 PIDs, 400 clients, no more than one cohort. Absolute UTC and monotonic hard stops supervise only the owned child process group; no unrelated PID is signalled.

Cumulative caps: serialized plaintext 10 GiB, compressed bytes 11 GiB, encrypted bytes 12 GiB. Plain and compressed streams are not retained on disk. Each compressed frame is encrypted and authenticated before writing; a chained authenticated footer commits the retained prefix. A bounded in-flight evidence reservation and a small actual free-space reserve are checked, without preallocating a million-request theoretical worst case or assuming compression. Hitting any cap/free-space reserve stops issuance and yields CAPACITY_INCOMPLETE/NP with the authenticated prefix retained. Lost evidence, writer blockage/failure, resource saturation and client scheduling gaps are reported separately and can invalidate load-generation adequacy. Raw request/response bytes, headers, timestamps, status, failures, explicit 0 and null are retained in encrypted NDJSON. Incomplete responses retain the bytes received and an explicit incomplete flag; they cannot pass.

No SUT restart, retry, auto-login, fixture regeneration or successor round. Session expiry, permission mismatch, inventory exhaustion, unexpected mutation, cap or deadline means stop and preserve the prefix. A full cohort is required for a performance verdict; postconditions and the independent conclusion are separate report fields. Server resource telemetry is supplied by the separate collector and joined by run ID/UTC.

Public preparation receipts may disclose the test kind, duration, counts, pass/fail and artifact hashes; they disclose neither case contents nor credentials. Local mock/calibration evidence is not SUT acceptance. A local 600-second timer gate verifies the timer and cohort completeness gate, not SUT performance.
